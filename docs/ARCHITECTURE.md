# Better X architecture decisions

Durable engineering decisions for Better X. Each entry states the decision and why. Change an entry only with a recorded reason; add new entries at the end of the relevant section.

Better X is a Chrome extension that combines a private post library (saving, collections, tags, notes, search, media downloads) with customization of X itself (cleanup, feed and post behavior, navigation, appearance).

## Foundation

**Based on Saved for X 0.2.0, not rewritten.** This repository starts at Saved for X commit `b6199ac` with its full history. Its repositories, download lifecycle, media resolver, overlays, extraction, and tests are working and tested; they change only for a concrete architectural reason. The 0.2.0 build is the equivalence reference for Stage 0 (see "Baselines").

**Chrome only, Manifest V3.** No Firefox or Safari abstractions unless something requires them. Modern Chrome APIs are allowed: `sidePanel`, MAIN-world content scripts, `document_start`.

**New extension identity.** Better X is a separate extension, not an update of Saved for X. Internal names (IndexedDB name, storage keys, download folder, CSS prefix, package name, feature IDs) may change freely; nothing is kept for browser-storage continuity. Since Stage 1A: IndexedDB `better-x`, `chrome.storage` keys `bx.*`, download folder `Better-X`, extension-owned CSS and DOM names prefixed `bx-`.

**Saved for X users migrate by export → import.** Better X must import Saved for X export files (`format: "saved-for-x"`) versions 1, 2, and 3, with the existing rules: local data wins, imported download history becomes `historical`, invalid history entries are skipped. Better X's own backups are `format: "better-x"`, version 1, which keeps the Saved for X version 3 structure; `src/lib/backup.ts` holds the importable formats and the upgrade from older versions (Stage 1B).

## Structure

**Saved and Downloads remain large modules.** The library/save control and the download system are imperative subsystems with their own UI and background services. They join the shared lifecycle and settings schema, but are not split into per-toggle features.

**Customization uses declarative feature definitions.** Each customization feature declares, as data: ID, section, title, description, settings with defaults and validators, dependencies, supported layouts (viewport width class and X markup variant), stability (`stable` / `beta` / `experimental`), required X capabilities, optional CSS, runtime hooks, and optional setup returning a disposer. A feature that throws during setup is marked failed and disabled; others keep running. The side panel renders Customize from the same definitions the content script runs.

**A shared X runtime owns page integration.** One runtime in the isolated content script owns:

- page observation and its lifecycle (global / page / modal scopes, disposed on route change);
- routes and SPA navigation;
- layout detection (wide vs narrow X layouts, test-ID vs newer markup);
- post discovery, including recycled post elements;
- timeline processing and post classification;
- action-row integration (ordered slots; the save control is one slot);
- popup and menu routing for X's own popups;
- styles (`html` data attributes, generated stylesheets, React Native stylesheet access).

Saved and customization features consume these services; neither keeps its own copy.

**Features do not create unmanaged observers.** Feature modules must not create ad hoc `MutationObserver`s, polling loops, or global listeners. All observation is owned and disposed by the shared runtime, and features receive events through runtime hooks. This is not a rule of "exactly one observer": the runtime may use a small number of focused observers (for example the document, `#layers`, `<title>`, the app wrapper) where that is cleaner or more efficient.

**The lifecycle foundation is `src/runtime/` (Stage 2A.1).** `Scope` owns cleanup: disposers, listeners (`listen`), animation frames (`requestFrame`), child scopes, and an `AbortSignal`. Disposal runs everything once, most recent first, and a cleanup that throws does not stop the rest. `observe(scope, target, options, callback)` creates a MutationObserver that disconnects with its scope. `waitFor(selector | predicate, { signal, timeout, root })` resolves on the first match using a short-lived observer (no polling) that is released when it settles. The content script owns one root scope, disposed through WXT's `ctx.onInvalidated`. WXT announces invalidation only when a newer copy of the script starts, so the scope also asks `ctx.isValid` (`Scope.alive()`) each time `observe` delivers, which is how an extension reload under an open tab is noticed; the global, page and modal scopes of the stages ahead are children of it. Still outside the scope: listeners and timers inside the large Saved and Downloads closure that are already tied to an overlay's own cleanup (closed on disposal), and in-flight save/download promises, which can still finish after disposal.

**Routes and layout are runtime services (Stage 2A.2).** `src/x/routes.ts` is a pure classifier from pathname and query to a `Route` (`id`, a `key` that is its logical identity, `modal`, and parameters); it never reads the DOM or the page title, and canonical post-URL parsing stays in `src/x/url.ts`. The key ignores hash, trailing slashes and tracking parameters but includes what changes the content (search text and filter, profile tab, a post's quotes/likes list). The composer and photo/video viewers are `modal`: they are routes, but not pages. `src/runtime/route.ts` follows navigation, notifies on a change of logical route, and owns `pageScope`, a child of the root scope that is disposed and replaced when the _page_ changes and left alone while a modal opens and closes over it. `src/runtime/layout.ts` reports `wide` or `narrow` from the flex direction of the element after `#layers` (a column is narrow, the same signal Control Panel for Twitter uses), re-read when that element's `class` changes, so opening the browser side panel is noticed without any route change; it rebinds if X replaces the wrapper and waits (additions only) if it is not rendered yet. Both are mirrored on `<html>` as `data-bx-route` and `data-bx-layout`, which the smoke test reads and later stages can style against.

_Navigation signal, from a spike (Chrome 154, isolated world)._ `window.navigation` is available to the content script, and its `currententrychange` fires for `pushState`, `replaceState`, back and forward, including a `pushState` that changes neither the DOM nor the title. `popstate` fires only for back/forward and hash changes, never for `pushState`, and the page title and DOM mutations are not reliable (a push can change neither). So the service listens to `currententrychange` alone: no polling, no history patching in the page world (Stage 7A), no title observer, no safety net on DOM batches. The extension requires Chrome 116, which has the Navigation API. The service takes its environment as a parameter and also works from `check()` alone, which is how it is tested. Not verified against a signed-in X session.

_Markup shape (test-ID vs newer layout) is deliberately not detected yet._ The extractor already tolerates both per article, with test-ID hooks first and shared structure as fallback. A page-level answer would have to be inferred from whichever posts happen to be loaded (none, on many pages, and a mix is possible), which is a heuristic that needs observation of real signed-out X pages that automation cannot currently reach (X returns 403 to automated Chrome). It should be added with the first feature that needs it, together with evidence, as a separate property from wide/narrow.

**Posts and the action row are runtime services; Saved is their first consumer (integration sprint).** `src/runtime/posts.ts` (`PostStream`) is the one place posts are discovered. It sits on the single managed document observer (`src/runtime/articles.ts`), so a consumer adds no observer and no scan. It reports each post whose element appeared (`new`), was reused by X for another post (`recycled`) or changed inside (`changed`: X renders a post in stages, so listeners must be idempotent), once per frame per element, skipping quoted posts; a listener can ask for a replay of the posts already on the page. `src/runtime/action-row.ts` (`ActionRow`) mounts `ActionSlot`s (id, order, `create`, `update`) into each post's action row: one element per slot per post element, re-targeted on recycling, recreated if X re-renders the row, ordered by `order`, ids unique, removed on unregister or scope end. The icon alignment that matches the row's native icons lives there and applies to every slot. `startRuntime()` composes these with routes and layout, and `src/saved/` (control, chip, menu, downloads, overlay, state sharing one `SavedContext`) is built on them. Anything that later adds an action registers a slot; anything that later reads posts subscribes to the stream; neither creates an observer. Post classification and timeline filtering are not part of the stream yet and should arrive with the first feature that needs them.

_Cleanup still outstanding._ Overlay-internal listeners are released only through `closeOverlay`; in-flight download progress callbacks end with their overlay but their requests run to completion; `requestAnimationFrame` and `setTimeout` calls inside the overlay code are still raw (released by the overlay's own cleanup); and the side panel and background have no lifecycle model, which they do not need.

**Customization features are registered definitions on the runtime (Customization MVP, expanded in the Customization expansion).** `src/features/` holds a `FeatureDef` per feature, of two kinds: a **toggle** (`id`, category, title, description, optional `keywords` for search, a default, optional `css`, optional `activate({ scope, runtime })`) and a **slider**, which is a toggle that also has a number (`min`, `max`, `step`, `defaultValue`, `unit`, and `css(value)` instead of `css`). The `id` is `category.name` and is what settings store, so an id that has shipped is never renamed. `createFeatureRegistry` validates the set at startup (well-formed ids in their category, no duplicates, sensible slider ranges, a default on its step) and resolves stored values: `enabled()` falls back to the default, `values()` takes a stored number, replaces anything that is not a finite number with the default, clamps it into the range and snaps it to the step, so a hand-edited or newer-build value can never push the page outside what the slider offers. `startFeatures` (the host) turns features on and off to match `settings.features` and restyles when a slider moves, at startup and live whenever any context writes settings, so every open X tab follows the side panel without a reload. Each running feature has its own child scope: switching it off, or a throw while it starts, releases exactly its work, and a feature that fails stays off without reaching Saved or the other features. All feature CSS goes into one `<style id="bx-features">` that is rewritten (never accumulated) and exists only while a feature with CSS is on. Features get the shared runtime and never create their own observers.

_The catalog._ 65 features in six categories (navigation, home and feed, posts, sidebar, appearance, ads/Grok/Premium), one file per category (`navigation.ts`, `feed.ts`, `posts.ts`, `sidebar.ts`, `appearance.ts`, `cleanup.ts`, plus the three hand-written ones, `hide-ads.ts`, `hide-grok.ts`, `hide-for-you.ts`), each built with `definitions(category)` from `define.ts` and the helpers in `css.ts` (`hide`, `rule`, `onRoute`, `links`, `cellWhere`). Everything except Hide For You is CSS only: nothing observes the page, a post X renders later is covered as it appears, and turning a switch off removes the rule. `docs/CONTROL-PANEL-INVENTORY.md` lists every Control Panel option, how it maps, and what was deferred and why. Selectors are scoped by `<html>` attributes the runtime publishes: `data-bx-route` (Home, profile, notifications...), `data-bx-layout` (wide or narrow) and `data-bx-sidebar` (present while X shows its sidebar column, from `src/runtime/sidebar.ts`: one child-list observer on the primary column's parent). A rule meant for one route, layout or sidebar state therefore does nothing elsewhere and cannot be stuck in the wrong state when Chrome's side panel narrows X.

_Rules must be cheap._ Style cost was measured on an X-shaped 200-post page (`perf/README.md`). A `:has()` whose subject is a bare `div` (`cell > div:has(x)`) made Chrome re-test every ancestor `div` of anything added to the page, about 5 ms of style work per rule per 200 posts. The same rule anchored where an attribute exists is nearly free: write `:has()` on the timeline cell (`cell:has(x) > div`, `cellWhere` in `css.ts`), on an element with a role or test ID (`aside[role="complementary"]:has(...)`), use child combinators inside `:has(> ...)`, or find the thing by a rare class (the composer's `.DraftEditor-root`). `src/features/catalog.test.ts` enforces what can be enforced (no X-generated class names, hiding rules need an attribute or id, balanced CSS); the rest is measured with the `--features` modes of `scripts/perf/run.mjs` (`cat:<category>`, `ids:<id>`), which is how every rule above was found and checked.

_Settings._ Version 2 added `features`, a map of feature id to boolean holding only what the user has set; version 3 added `values`, the same for slider numbers. A missing id is the feature's default (all are off; every slider's default is what it shows when first switched on), unknown ids are kept but ignored, and a stored version 1 or 2 object loads unchanged and becomes version 3 on its next save. In a patch, `null` forgets an id (back to its default), which is how resets, quick setups and Undo are written. Resetting appearance and Saved preferences keeps both maps. Settings are not part of the library export (JSON export and import carry bookmarks, collections and download history only), so they are unaffected by it.

_Sidebar cards._ A feature that hides a sidebar card cannot do it with `:has()` (see the rule-cost notes above) and a card's border and spacing sit on a wrapper above the `aside`. `src/runtime/sidebar.ts` is therefore a shared service (`runtime.sidebar`): it publishes `data-bx-sidebar`, exposes the column, and calls listeners once per frame when the column changes, observing it only while a listener exists. `hideSidebarCards` (`src/features/sidebar-cards.ts`) marks the whole card (`climbToCard`: up to the sections container, never past a neighbour or to the whole sidebar) with one attribute that the feature's CSS hides, and releases it when the card stops matching or the feature stops.

_Toolbar mode._ Settings v4 `openAs` is `sidepanel` or `popup`. Chrome opens a popup and never the side panel while the action has a popup, so `src/lib/launch-mode.ts` makes each mode clear the other (`action.setPopup`, `sidePanel.setPanelBehavior`), and the background worker applies the stored mode on every start (a run-time popup is not in the manifest, so only the worker can restore it) and on every settings change. The popup page is `entrypoints/compact` (an unlisted page, not `popup`, so the manifest has no `default_popup`): the same `App` with `mode="popup"`, a fixed 400x580 shell with its own scrolling (never a `vh` height: Chrome sizes a popup from its content). Both read and write `chrome.storage`, so they agree. Settings backups carry `openAs` since 1.1.5 (with `popupHeight`, `panelMode` and `panelHandle`, see "Settings backup"). The popup's height is a setting (`popupHeight`: 480, 580 or 600 px, set as `--popup-height` before the first paint and cached in `localStorage` like the theme); Chrome draws no extension popup taller than 600 px, so that is the tallest option, and reset keeps it like `openAs`. For more height there is a third mode, `window` (1.1.1, `src/lib/floating-window.ts`): the icon has neither a popup nor the panel on click, so the click reaches `action.onClicked`, and the worker opens the side panel page (`sidepanel.html?window`, App mode `window`) in a Chrome window of type `popup` that the person can move and resize to any size. Its bounds are saved on every `windows.onBoundsChanged` (`bx.windowBounds`) and reused; the first one is as tall as the browser window, against its right edge. Its id is kept in `chrome.storage.session`, so a second click focuses it. If Chrome refuses the remembered bounds (mostly off screen, a monitor that is gone), it opens at a default size instead. No new permission is needed.

_Settings backup._ `src/lib/settings-backup.ts`: format `better-x-settings` v2 (switches, slider numbers, theme and accent, the account lookup mode, and the country filter's countries, mode, scope switches and Always Show entries; v1 files still import), read defensively (size, JSON, format, version, shape, then each entry: unknown ids unsupported, bad types, out-of-range or off-step slider numbers, countries that are not real, handles X could not have, non-numeric ids invalid and skipped), applied in one write as merge (lists are added to) or replace (lists become the file's; a v1 file cannot name the filter, so it leaves it alone). Separate from the Library backup, which it refuses by name. The account cache and anything credential-like are never in it. Since 1.1.5 it carries every setting a person chooses: an optional `preferences` section (density, Show download options, After saving, the saved-post menu's actions, Ask where to save) was added without a version change (a file without it leaves those alone even on Replace; an older build ignores it), so the earlier rule that Saved and download preferences stay out is withdrawn at the owner's request (2026-11-09). A `launch` section (same rules) carries how Better X opens (`openAs`, `popupHeight`, `panelMode`, `panelHandle`), also at the owner's request, so a second browser opens it the same way; importing it changes the toolbar there, which the worker applies as for any settings change. Only caches and window/UI state stay out (`bx.overlay`, `bx.windowBounds`, `bx.windowId`, `bx.xmode`, the account cache, open Customize groups). `settings-backup-all.test.ts` lists every `Settings` field, so a new setting fails the tests until it is listed, and round-trips a setup with every setting and every feature changed.

_Account insights._ Four layers, each replaceable on its own.

1. **Adapter** (`src/x/about-transport.ts`, `about-account.ts`): the only place that knows X's `AboutAccountQuery` (id, URL, headers, response shape). It makes the page's own same-origin request from the content script with the page's `ct0` token read for that one request and the web app's public bearer token, keeps no cookie, header or token, and returns typed outcomes (`ok`, `notFound`, `rateLimited`, `unauthorized`, `unsupported`, `error`) plus X's rate headers. `parseAboutAccount` returns `AccountInfo` where a field X did not send is absent, never filled in; a response about another handle is refused. _Based in_ (`basedIn`), _connected via_ (`connection`, with its own platform enum) and a post's client are separate concepts and separate types.
2. **Service** (`src/insights/accounts.ts`, `accounts-store.ts`): cache keyed by handle with one entry per X account id (a rename drops the old handle), TTL 14 days for answers, one day for "unavailable", exponential backoff (2 min x3, cap 6 h) for failures, which never replace an older good answer. One lookup in flight per account; two lookups at a time, 500 ms apart; priority manual > pointer rest > visible, newest visible first; a queued lookup whose post scrolled away is dropped before it starts. X's `x-rate-limit-*` and `retry-after` headers, and 429, pause every lookup (shared with other tabs through `chrome.storage`); a refused session or a changed query pauses lookups for 10 min / 1 h. The cache is saved at most every 3 s under `bx.accounts` (3000 entries), merged across tabs by entry age, and cleared everywhere by removing the key.
3. **Runtime** (`src/runtime/accounts.ts`): `runtime.accounts.track(owner, article, handles, {auto})` is how a consumer says what a post shows; one IntersectionObserver serves every tracked post, and changes come back as "these posts need another look", coalesced per frame. Nothing exists until used.
4. **Consumers**: badges (`src/insights/badges.ts`, `card.ts`; one controller shared by the four toggles; delegated listeners, a single card element in `document.body`) and the country filter (`src/insights/filter.ts`, pure decisions in `verdict.ts`). The filter marks a timeline cell with `data-bx-filter` (a static CSS rule hides the cell's child, as other features do; the placeholder is a sibling of it) and a quote card with `data-bx-quote`; the author of each is read from its own name block, so a quote is never judged by the quoting post's author or the reverse. It only acts on an `ok` entry with a based-in place; unknown, loading, failed and unavailable accounts, Always Show accounts (by account id when known, else handle), the user's own handle and the post the page was opened on are exempt. No node is removed, so Saved's extraction (which reads the DOM) is unchanged, and a test pins that.

_Posting client — deferred._ A post's own client ("Twitter for iPhone") is a different field from the account's connection. The reference implementation (X-Source-label) reads the `source` of `TweetResultByRestId` through another internal query (its own id and feature flags, on `api.x.com`). That query id and its flag set rotate and cannot be checked from here, and an unverifiable second internal endpoint would add a failure mode for little. It is not built; when it is, it belongs behind the same adapter, on demand for the focal post only, never labelled as account data.

_Quick setups._ `src/features/presets.ts` declares Clean, Minimal and Focus as lists of feature ids (and slider numbers). Applying one replaces the customization switches with exactly that list through one settings patch; `restorePatch` writes back what was there for Undo, and `resetPatch` forgets features. They read and write only `features` and `values`; Saved, downloads and the panel's own preferences are never touched.

_The Customize view._ `src/sidepanel/Customize.tsx` renders the catalog: search (`customizeModel.ts`: every word must appear in a feature's title, description or keywords; the category name is deliberately not searched, the chips pick categories), category chips with counts, collapsible groups (`FeatureGroup`, open groups remembered in `localStorage`, closed groups `inert`), `Toggle` rows and `SliderRow` (a native range input, written to storage at most every 80 ms while dragging and once at the end, with a reset to default), quick setups with Undo, an empty state, and a confirmed "Turn everything off". It stays mounted while the Library shows, so its search, open groups and scroll are kept. Motion is CSS only (transitions 140-200 ms on transform, opacity, color and one grid track; the group panel opens by animating `grid-template-rows`), nothing animates on re-render, and the global `prefers-reduced-motion` rule switches all of it off. No component library was added: native checkbox switches and range inputs give keyboard and screen-reader behavior, Lucide (already present) gives the icons.

_Fragility._ These features depend on X's test IDs, roles, link targets, nesting and a handful of icon paths, taken from Control Panel for Twitter; none has been checked against live x.com (X blocks automated browsers), only against X-shaped fixtures in real Chrome. A failure shows up as a feature doing nothing, never as a hidden ordinary post: every hiding selector is required to contain an attribute or id (tested), pinned/community posts and Better X's own controls are excluded where a rule could reach them, and `posts.simplifyActions` removes only children of an action row that holds X's reply button, never `data-bx-slot` controls. Known soft spots: Hide For You's tab order is positional; `posts.hideShareButton` matches the share button's inline style as Control Panel does; the focused post's views are its 2nd and 3rd time-bar children; `posts.hideVerifiedBadges` hides every badge (Control Panel tells Premium from other badges with React props); `navigation.hideAccountSwitcher` and the width sliders use Control Panel's structural rules; `sidebar.hideFooter` matches an English label; `feed.hideManageTimelines` identifies the plus button by its icon, which is the one rule that still costs about 5 ms per 200 posts. X's newer markup shape (signed-out) has no test IDs, so none of them match there.

**X internals live behind a MAIN-world capability layer.** React props, X's Redux store, verified-badge props, router history, feature switches, XHR rewriting, and internal GraphQL are reached only from a MAIN-world module that exposes named capabilities through a narrow, batched message protocol. Capabilities are probed at startup; a failing capability disables only the features that require it and is reported in diagnostics. Fragile access paths live in one place each. Messages from the page world are untrusted: they never trigger settings writes, downloads, or library changes without validation in the isolated world.

**X themes are palettes, painted from a quarantined selector table (Themes).** `src/themes/` re-skins x.com itself (not the side panel, whose `theme`/`accent` keep their meaning). A theme is a seed of `#rrggbb` colors (`bg`, `text`, `accent`, optionally `raised`, `hover`, `border`, `muted`); `deriveTokens` fills the rest by mixing `bg` and `text` and guarantees `muted` and the link-text shade of the accent at 4.5:1 on `bg`, moving only those derived tokens, never the person's colors. Twelve presets (ids never renamed) and one Custom palette (settings v6 `xTheme: { active, custom, chat }`, default off). `buildThemeCss` writes one custom-properties block plus constant surface rules, every selector under `html[data-bx-theme]`, `!important` because X sets colors inline, into one `<style id="bx-theme">` (two text nodes, each rewritten only when it changes). Only validated hex reaches the stylesheet, and the builder re-checks every token before writing it.

_Why a quarantine._ X paints its surfaces with React Native Web atomic classes (`r-…`), jetfuel classes (`j-…`) and inline colors, which customization features are forbidden (`catalog.test.ts`). Themes cannot avoid them, so **hashed classes live only in `src/themes/surfaces.ts`**: a table of surfaces (role, color properties, kind, selectors, sources, verification state, note), seeded from Dim Mode for Twitter / X and Control Panel for Twitter. `surfaces.test.ts` keeps it to colors (an allow-list of properties; no layout, visibility, `url()` or `@import`), away from Better X's own UI, media and the verified badge, with text roles only on `color` and surface roles only on backgrounds and borders, so a selector that stops matching leaves a patch of X's black, never unreadable text. `scripts/theme/probe.js` is a console snippet the owner runs on live X; an entry becomes `verified: 'live'` only from its output.

_Early script and mode._ The theme runs in its own content script at `document_start` (`entrypoints/theme.content.ts`), because the main script runs at `document_idle` and every load would flash X's black first. It does not use the shared runtime: its own scope, one style element, and two small focused observers (`src/themes/detect.ts`): `<html>` for `data-theme`/`style` (and its children only until `<body>` exists) and `<body>` for `style`/`class`. X's mode is read from `<html data-theme>`, then `color-scheme`, then `<body>`'s inline background (white Default; black or `rgb(5, 5, 5)` Lights out). A theme applies only while X is in its base mode (all v1 themes are dark); otherwise `data-bx-theme` is removed, which switches every rule off at once. The last mode seen is cached under `bx.xmode` so the first frame of the next load is right; a wrong cache costs one frame. Reset keeps `xTheme`, like the feature toggles; settings backups carry it from format version 3.

_The Themes tab._ (Chat theming has no switch in 1.1.1: the owner put it on the back burner; `xTheme.chat` and its rules stay.) A third section beside Library and Customize (`src/sidepanel/Themes.tsx`), kept mounted while hidden like Customize; the tab list's arrow keys cycle through all three and wrap. It shows X's own Lights out, the presets and Custom as cards (`ThemeCard`: a button with `aria-pressed` and a miniature post drawn from the theme's tokens in CSS), writes only `xTheme`, offers Undo after a switch, and says when a theme is paused because X is in Default (read from `bx.xmode`). Custom opens `ThemeEditor`: Background, Text and Accent, four more colors under Advanced, a live preview, non-blocking contrast warnings, Start from a preset, and Reset to Lights out. Its color inputs are `ColorField`, extracted from `ColorRow` (which now uses it), so the picker, the 80 ms throttled drag and the complete-code-only hex box exist once. Customize's quick setups and Turn everything off never touch `xTheme`.

**The panel overlay draws the side panel inside X (1.1.5).** Chrome's side panel narrows the tab's viewport, so X re-centers and the timeline jumps; that is the browser's doing and no stylesheet can undo it, and counter-shifting X (margins, transforms) would break its `position: fixed` descendants. Settings v7 `panelMode` (`native`, the default, or `overlay`; side panel mode only) and `panelHandle` (an optional edge tab, off) choose instead to draw the panel inside the X tab. Both are kept by reset like `openAs`, and since 1.1.5 travel in settings backups with it (the `launch` section; the format stays at v3).

_The host._ `src/content/overlay.ts`, started from `content.ts`, creates nothing until the first open: then one `<bx-panel-overlay>` appended to `<html>` (outside X's tree), fixed right/top, `100vh`, max z-index, `contain: strict`, all inline and `!important`, with an open shadow root holding a resize grip and an iframe of `sidepanel.html?overlay` (App mode `overlay`: the same app, with a Close button instead of "Open in popup", and Esc closing it unless the key was used or an `aria-modal` dialog is open). Nothing of X's is styled or measured: no `<html>`/`<body>`/`#react-root` change, no observer, no per-post work; while closed the host is `display: none` and the only cost is one runtime message listener and one storage listener. It is non-modal (no backdrop; the host covers only the panel), slides with transform and opacity (off under `prefers-reduced-motion`), and takes the Library theme's light/dark/auto for its border and shadow. Leaving overlay mode removes the frame. `sidepanel.html` is web-accessible to x.com and twitter.com only.

_Spike results (Chrome 156, X's live CSP captured 2026-11-09)._ X's `frame-src` lists no `chrome-extension:`, yet an extension frame created by the content script (and even by the page) loads, while an ordinary cross-origin frame on the same page is blocked: Chrome exempts extension resources from page CSP. Inside, the app has every extension API and `tabs.getCurrent()` is the X tab. So one UI codebase in an iframe, not a second React mount in the content script. Only the page needs to be web-accessible, not its scripts and styles. CDP mouse input is not routed into the extension frame (the page receives it on the `<iframe>`), so the smoke test presses buttons inside the frame from script; real clicks are a manual check.

_State._ Open/closed and width (320-560, default 400, clamped) live under `bx.overlay` (`src/lib/overlay-state.ts`), not in `bx.settings`, like `bx.windowBounds`: toggling and resizing are frequent and must not wake every settings listener. Every X tab follows it, so the overlay is open or closed everywhere and restored on load and in new X tabs; the width is written on pointer release (or per arrow key on the grip).

_Toolbar click routing._ Three things were measured with real clicks (`page.triggerExtensionAction`): the worker cannot read an X tab's URL from content-script matches alone; with `activeTab`, `action.onClicked` gets `tab.url`; and `sidePanel.open()` fails after anything is awaited ("may only be called in response to a user gesture"), so a click that wakes a stopped worker cannot read the mode from storage and still open the native panel. Hence: overlay mode leaves Chrome configured exactly as side panel mode (`openPanelOnActionClick: true`, no popup), so on every other site Chrome opens its own panel with no code involved. Each X tab's content script, while overlay mode is on, sends `overlayTab` and the worker calls `sidePanel.setOptions({ tabId, enabled: false })` for that tab: Chrome's panel is hidden there (a native panel left open cannot narrow X) and a click on that tab goes to `action.onClicked`, which sends `bx.toggleOverlay` to the tab (`routeActionClick` in `src/lib/launch-mode.ts`). A per-tab disable survives navigation and `tabs.onUpdated` reports the same loading/complete for `pushState` as for a real navigation, so a tab that leaves X stays disabled; its click reaches `onClicked` with a non-X URL, and the worker gives the panel back and opens it in the same tick (verified), or, if that click woke the worker, only gives it back, so the next click opens it. Switching back to native, each X tab that had claimed itself sends `overlayTab` off. The shortcut is `_execute_action` (Alt+Shift+B), so it is the same click in every mode; the save menu's "Open bookmark library" opens the overlay directly. Manifest delta: `activeTab` (no install warning), `commands`, `web_accessible_resources`; no host permission and no new content script.

## Product defaults

**Conservative defaults plus presets.** Base defaults change nothing about X: every customization is off. The Customize view offers three quick setups (Clean, Minimal, Focus), each a list of feature ids applied through the same feature system with an Undo; they have no implementation of their own. A first-run chooser is not built.

**Full Twitter branding restoration is optional later.** Logo, favicon, title, and Tweet/Retweet wording are not in the initial stages. Nothing should prevent adding them.

**Twitter tab icon and title are features (1.1.1).** The owner asked for them (2026-11-08), so the favicon and title parts of the entry above are built: `appearance.twitterBird` and `appearance.twitterTitle` in `src/features/branding.ts`, off by default like every feature. Both touch only `<head>`: the bird is an inline SVG data URL set on X's own icon links (with a dot when X's icon is its notification `pip` variant), and the title replaces X's own name only where X names itself (" / X" at the end, " on X: ", a bare "X"). Each keeps one managed observer on `<head>` while on, because X rewrites both as you navigate, and puts X's own back when switched off. The logo in X's page and Tweet/Retweet wording are still not built.

## Baselines

**Functional baseline (Stage 0, 2026-10-04).** On the bootstrapped 0.2.0 source: `npm run check` passes, `npm test` 8 files / 60 tests pass, `npm run format:check` passes, `npm run smoke` 66 checks pass (65 in `run.mjs`, 1 in `restart.mjs`), and `npm run build` output is byte-identical to the shipped Saved for X 0.2.0 build.

**Performance baseline is a measurement, not a contract.** `npm run perf` loads the same offline X-shaped timeline with and without the built extension, alternating modes across repeated fresh-browser runs, and records medians and spread. The 0.2.0 result is `perf/baseline-0.2.0.json`; method and limits are in `perf/README.md`. Later stages compare against it, and a change is worth investigating when it falls outside the baseline's own run-to-run spread. There are no fixed pass/fail thresholds, and the harness never gates the functional checks.
